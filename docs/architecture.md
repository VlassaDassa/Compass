# Переход от прототипа к общей базе

## Данные и авторизация

1. Развернуть сервер приложения внутри корпоративной сети за HTTPS. Ограничения сети и авторизацию согласовать с владельцами инфраструктуры. Мобильные устройства получают доступ только утверждённым способом.
2. Подключить PostgreSQL по `schema.sql`, объектное хранилище для вложений и серверную авторизацию через корпоративный OIDC/LDAP-шлюз. Сам браузер к AD не подключается.
3. Администратор создаёт приглашения/активирует учётные записи и назначает роли. Сервер проверяет роль для всех административных операций. Клиентский интерфейс не является проверкой прав.
4. Сотрудники читают всю общую базу знаний, создают и редактируют статьи. Для вложений действуют те же права. Секреты находятся в отдельном сервисе и могут иметь более строгие права.
5. Версии статьи создаются в одной транзакции. Клиент передаёт `expectedVersion`; при конфликте сервер возвращает 409 и обе версии для ручного объединения. `effectiveFrom` — бизнес-дата, `createdAt` — время записи. История хранит полный снимок и автора. Восстановление создаёт новую версию.
6. Загрузки проверяются сервером по фактическому MIME, размеру и правилам ИБ. Изображения выдаются через авторизованный маршрут. Удалённые картинки из HTML не подгружаются автоматически.
7. HTML очищается на сервере проверенной библиотекой с allowlist. Клиентская очистка в прототипе — дополнительный слой, а не замена серверной валидации.
8. Настроить резервные копии БД и вложений, проверку восстановления, журнал админских действий и ограничение размера/частоты запросов.

## Контекст компании

Общая статья может содержать привязку к бизнес-центру и отделу, локальные исключения и дату начала действия. Политика поиска: общие материалы плюс подходящие центру и отделу, с явной маркировкой исключений. Список центров и этажей поступает с сервера; карта связана с идентификаторами оборудования и сотрудников, а не с текстом имени.

Адаптеры систем заявок и каталога должны быть read-only до отдельного согласования записи. В UI показываются состояние подключения, источник и время последней синхронизации. В прототипе эти места обозначены явно.

## ИИ и смена провайдера

Интерфейс обращается только к `POST /api/assistant/query` внутреннего сервера. Секреты провайдеров не уходят в браузер. Общий контракт `AnswerProvider` принимает разрешённый контекст и возвращает ответ, ссылки на версии источников и признак недостаточности данных.

- `ExternalProvider` вызывает согласованный внешний API через шлюз. Разрешённые классы данных и обезличивание задаёт организация. Закрытый контекст по умолчанию не отправляется наружу.
- `LocalProvider` вызывает локальную модель через совместимый API. Смена провайдера меняет серверный адаптер и конфигурацию; UI и поиск источников остаются прежними.
- Retrieval сначала выбирает актуальные версии по дате, центру, отделу и полномочиям пользователя. Ответ обязан содержать ссылки на эти версии; при недостатке данных помощник говорит об этом.
- Интернет-поиск — отдельный отключённый по умолчанию инструмент. Сервер формирует обезличенный запрос без имён, внутренних адресов, путей, доменов и секретов. Веб-источники помечаются отдельно от регламентов; они не могут отменять внутренние правила. Инструкции из найденных документов не считаются управляющими командами.
- При публикации статья получает задание на переиндексацию. Новая версия заменяет старую в индексе актуальных знаний, история остаётся доступной отдельно.
- Проверка дубликатов сначала использует полнотекстовый поиск, затем при подключении — embeddings. Результат содержит статьи и совпавшие фрагменты; пользователь выбирает дополнение, новую версию или отдельную публикацию.
- Пароли, ключи, персональные данные из хранилища доступов не участвуют в retrieval, embeddings и внешних запросах.

## Основные API

`GET /api/session`, `GET/POST /api/articles`, `GET /api/articles/:id`, `POST /api/articles/:id/versions`, `GET /api/articles/:id/versions`, `POST /api/articles/:id/restore`, `GET/PUT /api/me/favorites`, `GET/PUT /api/me/drafts/:id`, `POST /api/attachments`, `GET /api/people`, `GET /api/centers/:id/floors/:floor`, `GET/POST/PATCH /api/admin/users`, `GET /api/integrations/status`, `POST /api/assistant/query`, `POST /api/articles/check-similar`.

Локальный сервер Compass уже реализует минимальный режим общей рабочей области: `GET/PUT /api/state`, `GET /api/status`, `GET/PUT /api/ai/settings` и `POST /api/assistant/query`. Состояние прототипа хранится одной JSONB-записью, чтобы перенести весь интерфейс на PostgreSQL без потери данных; по мере появления авторизации записи можно разложить на нормализованные таблицы выше. Для production обязательно добавить OIDC/LDAP, серверную проверку ролей, аудит, резервные копии и отдельное хранилище секретов. Все подтверждения серверных операций должны опираться на успешный ответ API, а не только на изменение интерфейса.
